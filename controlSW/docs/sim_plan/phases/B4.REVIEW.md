## Review of link.py
- `_LinkState.deliver_time` implements `max(prev, send+lat+jitter, tx_end)` and then the stall push. In order, no drops. Bandwidth backlog uses a bucket from send time (`tx_end = max(bucket_free, send) + size/bw`). The test checks the slope.
- Stall hold-back is semantically right. A stall in progress at the item's base time pushes it to the stall end. Because `prev` is monotone, everything behind it is delayed too. A stall that ended earlier is a no-op. A stall starting after the item is delivered does not affect it. The `while` loop handles chained stalls. This is equivalent to, and cleaner than, the spec's per-item `+ stall_i`.
- Determinism: separate RNG streams (seed, seed+1). `schedule()` and the live emulator share one state machine. Tested.

2. [low] `iphone_replay_sender.py:128-129`: `next(ep.iter_main_frames())` and `next(ep.iter_uw_frames())` leave PyAV generators unclosed until GC. Harmless for a CLI.
3. [info] The app's default is `cameraFPS` 60 (DeploymentViewController.swift:137, 303-307, default index 1). The replay default of 30 follows the spec and the dataset. Docstrings say "30 or 60", which is accurate.
4. [info] client.py does not emulate the Swift `.error` event rule (SocketClient.swift:42-54), where a non-"Could not connect" string error causes an immediate reconnect. The validate-timeout and connect-retry paths are covered. Fine for the sim.
5. [info] Stalls never overlap (the next stall is drawn after the previous one ends), so the effective stall rate is a bit below nominal at high rates. Acceptable, and worth a line in B5/B6 docs if the rate is tuned.
