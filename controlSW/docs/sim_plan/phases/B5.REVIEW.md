## Findings
1. **Medium: `wireless_camera.py:412`.** The stale guard checks main only.
   - In v1, ultrawide is a separate socket on port 5556. If it drops while main stays up, the receiver keeps publishing a frozen UW image indefinitely. Only the `skew_main_uw_ms` health number would show it.
   - This matches the spec text (`t_main`), so it is not a spec miss, but it is a silent stale-data path into the policy.
   - Suggested fix: also return `({}, 0.0)` when `now - fu[1] > max_age_s` (or a looser UW bound), plus one test that kills only the UW stream.
2. **Low-medium: `clock_map.py:20-21, 144-158`.** The dejitter docstring says unconfirmed drops are stamped "up to T early". In fact a sender gap of n frames that is shorter than `window_s` stamps the next 2 frames about n·T early.
   - Reproduced: a 6-frame drop gives -195 ms on 2 frames, then correct stamps.
   - Gaps of 9 frames or more are caught by `max_age_s=0.3` (they are counted as stale ticks). Shorter gaps publish frames stamped up to about 0.3 s early.
   - Mitigation: dejitter is opt-in; no station yaml uses it (iPhone = arrival_minus_latency, rig = sender_stamp_ping).
   - Suggested fix: correct the docstring, or accept a drop at once when the inter-arrival gap itself is at least (n+0.5)·T.
   - Otherwise the algorithm is sound:
     - stamp <= arrival always, because the current sample is in the min and there is an explicit cap (`:165`);
     - with correct indices, lateness is the window's minimum delay, never more than the current delay;
     - a latency step below 0.9T shows up after `window_s`, as it should (true latency is not absorbed);
     - steps of 0.9T or more are read as drops (aliased modulo T), and the stamp stays at or below arrival;
     - sender/host rate drift is bounded at about window × ppm: 1000 ppm gives about 3 ms, and the envelope does not run away, because old samples age out.
3. **Low (for B7): `clock_map.py:181-198`.** The sign convention (θ = sender - host), the min-RTT offset and the windowing are correct. Two weaknesses on real Wi-Fi:
   - The fit anchors on a single min-RTT sample and extrapolates with a slope fitted to 8 bin minima.
   - In my simulation (20 s window, exponential RTT jitter of 4 ms per direction), the estimated drift was -91 to +91 ppm against a true 30, and |θ error| p95 was 1.1-1.8 ms (max 3.9 ms). Offset-only would be about 0.6 ms worse in the worst case from drift.
   - Consider anchoring at the regression intercept, or a longer window, once B7 measures real RTTs. The sim (symmetric pings) is fine.
4. **Low: `wireless_camera.py:263-276`.** The engineio patch is guarded at install time and copies the driver table per server, so it is safe if the internals move. Versions checked: simple-websocket 1.1.0 has `receive_bytes`, engineio 4.14.0.
   - Residual risk: if a future simple-websocket drops `receive_bytes`, the failure happens per connection inside `SimpleWebSocketWSGI.__call__`, not at patch time, so the client would be stuck on polling. Health/preflight would show `transport: polling`.
   - Pin the versions or check `inspect.signature` at patch time.
5. **Info.** Not defects; acceptable as built:
   - `sys.setswitchinterval(0.5 ms)` (`:539`) is set in `main()` only, i.e. in the dedicated camera process. Its cost is some extra context-switch CPU.
   - Frame-store tuples are replaced whole under `_lock`, and arrays are never mutated, so the store is thread-safe.
   - The fixed-rate tick resyncs after an overrun (`:404-408`).
   - `close()` shuts the servers down and the remaining threads are daemons.
   - v2 drops frames until the first ping, but the ping burst runs right on hello; `unsynced_dropped` was 0 in the test.
   - Transport is recorded on connect and refreshed in `stats()`, so upgrades are reported.
   - The counters `packet_errors`/`validates` are updated without a lock (they are approximate; health only).
