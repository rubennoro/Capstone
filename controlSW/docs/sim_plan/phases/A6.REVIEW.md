## Findings
1. **GT vs Judge t0 (not a bug; B9 Part 2 action).** stage3.py:435-440 takes the Judge's `t0 = time.monotonic()` after `wait_event` returned `episode_start`, i.e. after task-log tail polling (50 ms sleeps plus stdout latency). GT anchors at the task's own `episode_start` `t` (ground_truth.py:384-386). So `t_success_s` (relative) differs by `t0 - t_ep_start`, and the timeout shifts the same way. The absolute decision times agree (same sample, 100 Hz vs 25 Hz: dt <= 0.05 s). Success flags agree. B9 Part 2 should either read the `episode_start` `t` from `ep_dir/events.jsonl` and pass it as `t_start` to `Judge`, or compare `t0 + judge.t_success_s` with GT `t_success_mono` (GT already emits it), and write `t0` into `sim_truth.json`. `ev[1]` from `wait_event` has no `t`.
2. **`slip_m` is arm overshoot, not slip (confirmed).** Probe (`$S/a6rev/probe2.log`): eraser-minus-TCP z is constant to 0.2 mm through the lift (true in-hand slip 0.00 mm). The TCP overshoots its target after the 1 s lift by 5.0 mm (panda), 7.7 mm (fr3), 4.0 mm (panda +10 cm/-y), after a 14.7 mm lag; eraser z falls by the same amount, hence GT `slip_m` 5.3-10.9 mm > `slip_tol_m` 2 mm on every *successful* run. Judge and GT report it only, so no test breaks, but B8/B9 must not gate on `slip_exceeds_tol` in sim. Fix when wanted: add the TCP z (or eraser-minus-TCP z) to the sim line and judge state (additive), A7/A8 time. Real-arm data would show the same effect.
3. **Grasp height deviation 2 is right; the 0.01 placeholder is inconsistent with the model.** model.py:372-380 puts the TCP at the pad centre, pads are 30 mm long, so TCP 0.01 puts the pad bottoms 5 mm into the table (scene.py:59-65). A3 is not affected: stage1_replay.py:190-194 excludes pads from the table pairs (reports `pad_table_min_m` separately), and the +0.02 sensitivity already exists (`results/stage1/sensitivity_grasp_h0.02.log`: 43/45 on both arms; FR3 tool clearance 8.2 mm all demos / 14.3 mm feasible). STATUS.md says that run was unfinished: it is finished, update the note. Open question for the user: is the real TCP the pad centre? If it is, the station's `grasp_tcp_height_m` should become 0.018 (Track B).
4. **The 0.07 mm margin.** With 3 mm pad clearance the nominal 2.5 s / 1.5 s descent undershoots its target by 2.93 mm (panda) / 2.94 mm (fr3) (probe2). The test passes 10/10 but is on the table edge; a slightly different seed set or A4 retune could turn it into reflex flakes. Suggest `PAD_TABLE_CLEARANCE_M` 0.005 (scene.py:31), or a slower final descent. Not blocking.
5. **20 N reflex at 1.5 s approach: a real pad-table strike, amplified by the sim controller.** At trip, no arm contact; both fingers press the table at ~40 N each (dist -0.05 mm). Cause: after a 1.5 s approach over ~0.4 m (peak ~0.5 m/s, 2x the 0.25 m/s `v_max` in criteria) the TCP is 21 mm below its target, then a 1.0 s descent consumes the 3 mm clearance. 1.5 s / 1.5 s passes. So the threshold is not an artefact (20 N matches libfranka defaults; the real value is still the HW placeholder `collision_thresholds`). The overshoot is exaggerated by the sim: `joint_frictionloss_scale` 0 and the example-controller law `D = 2*zeta*sqrt(K)` is not mass-normalised (underdamped, A4). For the success rule and v_max: keep `v_max <= 0.25 m/s` (that keeps the sim in the passing regime), and in Stage 3 count reflexes as policy failures but report `pad_table` contacts separately. Do not raise the threshold to hide this.
6. **/dev/shm leak: owner Track B (launcher tests run unlocked), not A6.** At 11:03 there were 8 `rmq_ruben_{81134,81343}_right_wrist_camera_0_*` segments (dead pids, 2 x 512 MB each set), created 11:01:58 / 11:02:11 by B10's unlocked launcher pytest run. They were gone by 11:28 (someone cleaned; I did not touch them). After my locked full franka_deploy and franka_sim suites (which include the e2e and `kill_sender` launcher tests) `/dev/shm` had no rmq segments, so no test leaks on its own: it needs a launcher run that dies or overlaps another (the executor's 10:56 pid 77568 case overlapped B10 too). `Launcher` teardown only removes segments of its own child pids (launcher.py:1095-1097). Suggest B: make `preflight.shm_clean` ignore (and report) segments whose pid is dead; require `flock` for launcher tests.
